# Reference design: chat system

This is one reasonable answer. The hard parts are ordering, offline delivery, and multi-device sync.

## Protocol

Use a persistent WebSocket for online clients and a REST API for history and fallback sends.

```text
Client -> Server
  message.send   { clientMessageId, conversationId, body, attachments }
  receipt.read   { conversationId, messageId }
  typing.start   { conversationId }
  presence.ping  {}

Server -> Client
  message.new    { messageId, conversationId, seq, senderId, body, createdAt }
  message.ack    { clientMessageId, messageId, seq }
  receipt.update { conversationId, messageId, userId, state }
  presence.update{ userId, state, lastSeenAt }
  sync.batch     { messages[], nextCursor }
```

Every send carries a `clientMessageId` generated by the client. The server stores it and returns the canonical `messageId` and `seq`. Retries with the same client id are idempotent.

## Ordering

Each conversation has a monotonically increasing `seq` assigned by a per-conversation sequencer. Clients sort by `seq`, never by wall-clock time.

Two common implementations:

- **Single-writer partition:** one sequencer owns a conversation at a time, either in memory or via a lease. Simple and strictly ordered.
- **Storage sequence:** the database assigns a sequence per conversation on insert. Easier to operate, but requires a strong guarantee from the store.

The `(conversation_id, seq)` pair is the primary key and the ordering contract. A message is acknowledged to the sender only after it is durably stored and sequenced.

## Data model

**Messages** (wide-column store such as Cassandra/Scylla, or a partitioned relational table):

| Field               | Notes                                    |
| ------------------- | ---------------------------------------- |
| `conversation_id`   | Partition key.                           |
| `seq`               | Clustering key; per-conversation order.  |
| `message_id`        | Global id for receipts and dedupe.       |
| `sender_id`         | Author.                                  |
| `body`              | Text or a reference to object storage.   |
| `created_at`        | Server timestamp for display only.       |
| `client_message_id` | Unique per sender; used for idempotency. |

**Conversation members:** `(conversation_id, user_id, joined_at, last_read_seq)`. Kept in a relational store or a wide-column table.

**Receipts:** `(message_id, user_id, state, updated_at)` where state is `delivered` or `read`. Aggregate per conversation for group chats.

**Per-device cursor:** `(user_id, device_id, conversation_id, last_delivered_seq)`. This is what makes reconnect sync cheap.

**Presence and typing:** Redis keys with a short TTL, not durable storage.

## Architecture

```text
Client -> WebSocket gateway -> chat service -> sequencer -> message store
                |                    |                         |
                |                    +-> fan-out -> gateway sessions
                |                    +-> delivery queue -> push service
                |
                +-> presence service (Redis TTL)
                +-> history service -> message store + cache
```

- **WebSocket gateway** owns connections, authenticates sessions, and maintains a registry of `user_id/device_id -> connection`. It does not store messages.
- **Chat service** validates the message, persists it, obtains a `seq`, and publishes it for fan-out.
- **Fan-out** delivers to online recipients through their gateways. Large groups are fanned out asynchronously through a queue.
- **Push service** sends APNs/FCM notifications to offline devices. The push payload contains ids, not the full message when encryption or size limits matter.
- **History service** serves paginated history and reconnect sync from the message store and a short-lived cache.
- **Presence** is a heartbeat with a TTL. It is best-effort and should never block message delivery.

## Send, deliver, and sync

1. Sender posts `message.send`.
2. Chat service checks membership, writes the message, and obtains `seq`.
3. The sender receives `message.ack` with the canonical ids.
4. Fan-out looks up online devices and pushes `message.new` to each gateway.
5. Offline devices get a push notification; when they reconnect they call `sync` with their per-device cursor.
6. Receipts are written as devices acknowledge delivery and as users read. Receipts are aggregated for groups.

Delivery is at-least-once. Clients dedupe by `message_id` and `client_message_id`.

## Scale

500 million messages/day is about 5.8k messages/second average, with peaks several times higher.

- Shard the message store by `conversation_id`. A conversation stays on one shard, which keeps ordering local.
- Gateway connections are sharded by user; a user's devices can connect to different gateways.
- Group fan-out is bounded: small groups fan out inline, large groups fan out through a queue and may use a pull model for very large groups.
- Cache recent conversation windows for fast history reads.
- Retention: keep recent messages hot, archive older messages to object storage, and keep indexes for search if required.

## Trade-offs

- **Single-writer sequencing vs database sequences:** single-writer is strictly ordered and simple to reason about but needs failover; database sequences are easier to operate but depend on the store's guarantees.
- **Fan-out on write vs read:** write fan-out makes delivery fast for small groups but explodes for large groups; read fan-out is cheaper for large groups but adds latency.
- **At-least-once vs exactly-once:** at-least-once with client dedupe is practical. Exactly-once delivery across devices is much harder and rarely worth it.
- **Presence accuracy vs cost:** frequent heartbeats improve accuracy but increase load. A short TTL plus last-seen timestamps is usually enough.
- **Durable history vs ephemeral messages:** retention drives storage cost and privacy obligations. Make it a product decision, not an accident.

## Failure modes and monitoring

- **Gateway disconnect:** clients reconnect with exponential backoff and a cursor; the server replays missed messages.
- **Duplicate delivery:** dedupe on `message_id` and `client_message_id`; keep the dedupe window long enough to cover retries.
- **Sequencer hot spot:** a very active conversation can overload one shard. Split large groups or move to a pull model.
- **Store outage:** queue sends, return a retryable error, and never acknowledge before durability.
- **Push provider outage:** messages remain available on reconnect; surface a delayed-delivery state.
- **Clock skew:** never use client timestamps for ordering; use server `seq`.
- **Monitoring:** track send-to-ack latency, delivery latency, fan-out queue lag, reconnect rate, duplicate rate, store error rate, and push failure rate. Alert when fan-out lag or reconnect rate spikes.
